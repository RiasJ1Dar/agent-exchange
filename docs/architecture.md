# Архітектура

Чотири крейти в одному workspace. Залежності йдуть в один бік:
`ui` і `mcp` спираються на `render` і `store`, `store` не знає ні про кого.

| Крейт | Відповідальність | Рядків |
|---|---|---|
| `store` | SQLite: повідомлення, замки, міграції. | ~2000 |
| `render` | Складання `NOW.md` і `agent_talk.md`. | ~2900 |
| `mcp` | Протокол, кадрування, сім інструментів. | ~2800 |
| `ui` | HTTP-переглядач, база **тільки на читання**. | ~2400 |

## Схема бази

```sql
CREATE TABLE messages (
    id         INTEGER PRIMARY KEY AUTOINCREMENT,
    ts_unix    INTEGER NOT NULL,
    v          INTEGER NOT NULL,
    from_agent TEXT NOT NULL,
    to_agent   TEXT NOT NULL,
    topic      TEXT NOT NULL,
    op         TEXT NOT NULL,
    body       TEXT NOT NULL,
    read_at    INTEGER,
    sig        TEXT,          -- підпис Ed25519 у hex; NULL — не підписано
    key_id     TEXT           -- яким ключем підписано
);

CREATE TABLE locks (
    topic    TEXT PRIMARY KEY,
    holder   TEXT NOT NULL,
    taken_at INTEGER NOT NULL,
    ttl_sec  INTEGER NOT NULL,
    note     TEXT NOT NULL
);

CREATE INDEX idx_messages_inbox ON messages (to_agent, read_at, id);
```

Прочитаність — це `read_at`, а не булеве поле: видно не лише *чи* прочитано,
а й *коли*. Прочитані з `ts_unix` старшим за 14 діб прибирає внутрішній gc
на `post`/`ack` (не частіше ніж раз на годину на одному з'єднанні).
Непрочитані не чіпає. Окремого MCP-інструмента немає.

`from_agent` і `to_agent` — довільні рядки, а не перелік. Сервер не знає,
як звуть агентів; у `to_agent` окремо живе `*` — «усім».

## Міграції

Версія схеми живе в `PRAGMA user_version`. Приведення до потрібної версії
йде однією транзакцією `BEGIN IMMEDIATE … COMMIT`, і версія перечитується
**повторно вже під write-lock** — інакше два процеси, що стартують разом,
обидва вирішили б мігрувати.

База, новіша за збірку, не відкривається взагалі: краще відмова, ніж запис
у схему, якої ця збірка не розуміє.

| Версія | Що змінилось |
|---|---|
| 1 | базова схема |
| 2 | широкомовна адреса `Both` перейменована на `*` |
| 3 | `messages.sig` і `messages.key_id` — місце під підпис |

### v1 → v2, широкомовна адреса

```sql
UPDATE messages SET to_agent = '*' WHERE to_agent = 'Both';
```

Назва `Both` мала сенс, поки агентів було рівно двоє: у схемі стояло число
учасників замість ролі адреси. Зміст рядків при цьому не змінився — у світі
з двох агентів «усім» і «обом» те саме, — тож це перейменування, а не
втрата адресації.

⚠️ **Читання розуміє обидва написання назавжди**, а не лише під час
міграції. Причина конкретна: переглядач відкриває базу read-only і мігрувати
не вміє **за побудовою**, тож схема v1 для нього — звичайний робочий
випадок, а не залишок минулого. Показати нулі там, де лежить неотримане,
гірше за зайву гілку в `WHERE`.

⚠️ **Відкат після міграції потребує резервної копії бази.** Стара збірка
відмовиться відкрити схему v2 (`SchemaTooNew`) — саме так, як задумано, щоб
не писати в схему, якої не розуміє. Повернути старий бінарник **без**
відновлення бази не вийде.

### v2 → v3, місце під підпис

Дві NULL-абельні колонки. NULL не тимчасово: підпис вмикається конфігом, і
без нього рядки лишаються без підпису назавжди — обов'язкові колонки
означали б вимагати ключів від кожного, хто просто хоче поштову скриньку.

⚠️ Міграція, що додає колонку, **мусить бути ідемпотентною**. Нова база
створюється з повної схеми — тобто вже з цими колонками, — а потім однаково
проходить `migrate` з версії 0. Голий `ALTER TABLE ADD COLUMN` там падає з
«duplicate column name», і жодна нова база не відкривається взагалі.

Сам підпис описаний окремо: [Підпис](signing.md).

## Кадрування MCP

Транспорт — stdio, JSON-RPC 2.0. Підтримуються **обидва** кадрування:

- по одному JSON на рядок (основне);
- `Content-Length` у стилі LSP.

Тип визначається за першим байтом: `{` — рядкове кадрування, інакше
заголовки. UTF-8 BOM перед першим повідомленням теж переживається.

Стеля кадру — 1 МіБ. Довший не читається в памʼять цілком: хвіст
відкидається, клієнт дістає `-32700`, потік лишається живим.

## Чому без async

Навантаження — десятки повідомлень на добу від двох агентів. Асинхронне
середовище тут додало б залежностей і способів помилитися, не додавши
нічого корисного. `ui` обслуговує зʼєднання послідовно і цього вистачає.
